# Homework 3 — Specification-Driven Design

## Student & task summary

Peter Moroz. This homework produces a specification package (no code) for a **Virtual Card Lifecycle & Spending Controls** feature: a cardholder can create a virtual card, freeze/unfreeze it (including a system-initiated freeze from a fraud/velocity signal), set a daily spending limit, view paginated transaction history, and receive notifications on limit/freeze events. The deliverables are `specification.md`, `agents.md`, `.claude/rules.md`, and this `README.md`.

## Rationale

**Why this scope.** The seed requirements offered the full virtual-card lifecycle plus several optional extras (spending caps, replacement, disputes, notifications). I deliberately narrowed to create / freeze-unfreeze / limits / transaction view / notifications and left out replacement and dispute intake. The reason is depth over breadth: the homework is graded on traceability and decomposition, and a 6-7 objective spec spread thin produces shallower tasks than a 5-objective spec spread deep. The one addition beyond the literal seed list — a **system-initiated freeze triggered by a fraud/velocity signal**, only liftable by Ops/Compliance — was deliberate: it turns an otherwise simple CRUD feature into something with a real concurrency edge case (a user trying to unfreeze a system-frozen card, or two writers racing on freeze state) and a real compliance angle (who is allowed to undo what), which is exactly the kind of thing the grading rubric rewards ("anticipate failure modes... non-functional expectations").

**How performance targets were chosen.** Every number in `specification.md`'s performance table is explicitly labeled an *assumed target* with a one-line justification (e.g., card creation ≤2s benchmarked against typical card-network tokenization round trips; the 500ms freeze/limit visibility budget chosen specifically because it bounds the TOCTOU window described in Edge Case #5). I split the budget into "the write becomes visible to the authorization path" (500ms) versus "the authorization check itself" (50ms) because those are different engineering problems — one is about read consistency, the other about hot-path compute — and conflating them into one vague "fast" requirement would have hidden that.

**How verification depth was chosen.** Rather than a generic "write tests" bullet, the Verification section maps each of the 5 mid-level objectives to specific test categories (boundary tests for limits, concurrency simulation for freeze races, dedupe-window tests for notifications) and ties the production-grade reconciliation job (low-level task 15) into verification as an *ongoing*, not just pre-release, check — because a regulated authorization path needs a way to catch the accepted TOCTOU risk in Edge Case #5 after the fact, not just prevent it in a unit test.

**Alternatives considered and rejected.** A few choices in the spec look obvious in hindsight but had a real competing option:
- *Reconciliation cadence — hourly batch vs. real-time streaming.* A streaming reconciler (consuming the same event stream the authorization path writes to) would close the TOCTOU window in Edge Case #5 faster, but it adds a second always-on consumer of the authorization event stream purely for a risk that's already bounded by the 500ms staleness budget and is rare by construction. For a feature at this scope, an hourly batch job is simpler to specify, reason about, and (eventually) operate, and "catch it within an hour" is an adequate compliance posture for a low-probability, bounded-magnitude race — not "catch it within a second." Streaming reconciliation would be the right call if the authorization volume or risk tolerance were higher; it was rejected here as disproportionate to the actual exposure.
- *Pagination — cursor/keyset vs. offset vs. a different keyset key.* Offset pagination was rejected outright (Edge Case #8) because `OFFSET n` drifts under concurrent inserts — a card with active spend would see duplicate or skipped transactions across pages. Within keyset approaches, the spec keys the cursor on `(created_at, transaction_id)` rather than `transaction_id` alone, specifically because `transaction_id` is a UUIDv4 with no temporal ordering — a single-column UUID cursor would not produce a chronological page order at all. The compound key was chosen over a sequential auto-increment id (which would sort correctly with a single column) because no such column exists in this spec's hypothetical schema and introducing one purely for pagination would leak transaction-volume information through the cursor.
- *Scope — dispute intake vs. card replacement as the cut feature.* Both were in the seed list; only one extra mid-level objective would fit without diluting task depth. Card replacement was kept conceptually closer to what's already speced (it's mostly `createCard` + a decommission step for the old card) and would have added the least *new* surface. Dispute intake was cut instead of replacement because it pulls in a genuinely different domain — chargebacks, evidence collection, network-specific dispute windows — that doesn't reuse any of the freeze/limit/authorization machinery already built out here, so including it would have meant either a shallow treatment (defeating the depth goal) or a second, unrelated state machine competing for the same task budget.

## Revision notes

After an initial pass, a self-review pass closed several gaps that a careful implementer would have hit: the card status transitions were described in prose but never tabulated (now a full 4×4 matrix); `currency_mismatch` looked contradictory next to "single-currency assumed" (now explicitly scoped as a defensive check, not multi-currency support); permissions were scattered across edge cases rather than centralized (now one Roles & Permissions table); `platform_min_limit_minor` was referenced but never defined (now in the constants list, task 16); the `CARD_CREATED` notification trigger wasn't actually listed under M5 (now is); and the authorization check didn't verify the parent account was still active, which would have let a closed account keep spending through an existing card (task 8 now checks account status explicitly). Notification templates referenced in task 13 are now named (`card_created_v1`, `card_system_frozen_v1`, `transaction_declined_v1`) instead of left abstract.

A second self-review pass caught: (1) task 8's account-status check originally suggested a "cached" flag, directly contradicting `agents.md` Domain rule #5's ban on cache-backed authorization-path reads — reworded to require a strongly-consistent, synchronously-replicated read instead, so the two documents no longer disagree; (2) task 7's precondition still read `0 < daily_limit_minor`, ignoring the `platform_min_limit_minor` floor task 16 claimed it enforced — task 7 now states the floor directly; (3) `expiry` was promised to the cardholder in M1 but absent from task 1's schema — added as `expiry_month`/`expiry_year` on the card record itself (not vault-only, since expiry alone isn't a sensitive credential), with task 2's output updated to match; (4) task 7 had no account-status precondition even though Edge Case #7 claimed `setLimit` enforces `account_closed` — task 7 now checks account status directly instead of relying on the edge case to carry behavior the task itself didn't specify.

A third pass fixed two staleness issues left behind by the prior edits: the Ending Context's one-line card-table summary still listed the pre-revision schema (missing `expiry_month`/`expiry_year`/`vault_token`/`updated_at`) — now matches task 1 verbatim; and task 16's closing note referenced "the `> 0` rule in task 7" after task 7 had already been changed to a `platform_min_limit_minor ≤ ... ≤ platform_max_limit_minor` range — now references the actual range.

A fourth pass added **rate limiting**, which the homework's own template (`specification-TEMPLATE-example.md`) flags as expected for an API spec but which was entirely absent here. Added: a Rate Limiting & Throttling subsection under Non-Functional & Policy (per-account mutating-action budget, a tighter `createCard`-specific budget, a generous read budget, and an explicit note that this protects the management APIs, not the `evaluateAuthorization` hot path); a `rate_limited` error code added to the taxonomy everywhere it's enumerated; a new low-level task 17 specifying the throttle layer and its acceptance criteria; and corresponding rules in `agents.md` (Domain rule #6) and `.claude/rules.md` (a pattern to follow and a "never audit a rate-limited rejection" rule).
